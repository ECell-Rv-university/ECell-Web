# Development Guide

## Prerequisites

- Node.js 24.x (`.nvmrc` and `package.json`)
- npm and a modern browser
- Git

No application runtime environment variables are currently required for local development.

## Setup

```bash
nvm use
npm ci
npm run dev
```

Then open `http://localhost:3000`. Use `npm ci` for a reproducible installation from `package-lock.json`; use `npm install` when intentionally changing dependencies.

## Scripts

| Command | Purpose |
| --- | --- |
| `npm run dev` | Start the Next.js development server |
| `npm run build` | Create a production Next.js build |
| `npm run start` | Serve an existing production build |
| `npm run typecheck` | Run strict TypeScript checks without emitting files |
| `npm run lint` | Run ESLint |
| `npm run test` | Run Vitest once |
| `npm run test:watch` | Run Vitest interactively in watch mode |

## Recommended workflow

1. Read [`CONTRIBUTING.md`](../CONTRIBUTING.md) and the relevant files before editing.
2. Create a focused branch such as `feature/...`, `fix/...`, or `refactor/...`; do not work directly on `main`.
3. Keep section work inside its feature unless a shared change is intentional and coordinated.
4. Test visual work across viewport sizes, keyboard input, touch behavior where relevant, and reduced motion.
5. Run the complete validation sequence before opening a pull request.

```bash
npm run typecheck
npm run lint
npm run test
npm run build
```

## Component conventions

- Use TypeScript and type public data shapes and component props.
- Follow the existing default-export convention for components.
- Use PascalCase component and section directory names.
- Keep feature-only CSS, data, hooks, and animations with the feature.
- Keep sections independently placeable and responsive.
- Avoid negative-margin contracts or selectors that depend on sibling internals.
- Reuse shared tokens from `src/styles/global.css`.
- Import GSAP/ScrollTrigger through `src/utils/gsapSetup.ts`.
- Use the shared Lenis helpers for programmatic scrolling.
- Clean up observers, event listeners, GSAP contexts/timelines, and animation frames.

## Next.js conventions

This repository uses Next.js 16.3, whose local APIs and conventions may differ from earlier releases. Before changing framework behavior, consult the matching documentation installed under `node_modules/next/dist/docs/`.

Keep route metadata and static generation in server files. Add `"use client"` only to components that need client state, effects, event handlers, or browser APIs. In current dynamic routes, `params` is asynchronous and must be awaited.

## Styling

Although CSS lives next to features, imported `.css` selectors are global. Prefix selectors to prevent collisions. Tailwind CSS 4 is available through `app/globals.css`, but much of the current design uses vanilla CSS and shared custom properties.

When changing pinned or measured layouts, validate scroll behavior after fonts, images, and videos load. Favor transform/opacity animation and provide a reduced-motion result.

## Assets and performance

- Prefer WebP or another optimized web format for photographs.
- Use Next Image when appropriate and supply correct dimensions and alt text.
- Keep stable URL assets in `public/`; keep imported feature assets in `src/assets/`.
- Pause continuous video/WebGL work when hidden if practical.
- Avoid adding large client dependencies without discussion.
- Pin exact versions when adding a dependency and commit the lockfile update.

## Environment and secrets

`.env.local` and `.vercel/` are local/ignored. Never commit tokens or project identifiers. Deployment workflows consume these GitHub secret names:

- `VERCEL_TOKEN`
- `VERCEL_ORG_ID`
- `VERCEL_PROJECT_ID`

A local `VERCEL_OIDC_TOKEN` may be generated by tooling, but the application source does not read it. Never copy secret values into documentation, code, logs, or pull requests.

## Commit and pull-request expectations

Use focused commits with meaningful prefixes such as `feat:`, `fix:`, `refactor:`, or `docs:`. A pull request should explain what changed, why, how it was validated, and include visual evidence for UI changes. Confirm there are no browser console errors, unused files, accidental generated files, or unrelated formatting changes.
